My thoughts on the plan

What I would keep, add and cut

The two documents are thorough and the flow is right. These are the changes I would make so the product feels simple to a first-year student and stays affordable on Hostinger.

Keep

One app for everyone, role-aware

Members, guests, coordinators and check-in volunteers all use the same Flutter app. Extra tools (Scan, Team) appear only when that person holds a role for an event, and disappear after it closes. No separate "volunteer app" to install.

Add

Event-day mode

On the day of a registered event, Home turns into a single saffron card: today's duty, reporting point, gate, team lead's call button, and the pass one tap away. Everything else steps back.

Add

Bilingual from day one

English plus Hindi at launch, with Telugu and other state languages added as plain translation files. Switching language is on the sign-in screen, not hidden in settings. Fonts chosen here render Devanagari and Latin from one family.

Add

Pass that works with no signal

Large venues lose network. The QR pass is cached on the phone as a signed, time-limited token, and scanners queue check-ins offline and sync when back. Members never see a spinner at the gate.

Add

Scope switcher in the admin

A person can be District Admin of Hyderabad and Event Coordinator of one conference. The admin top bar always shows the active scope ("Telangana › Hyderabad") and every number on screen follows it. This prevents most "why can I see this?" confusion.

Defer

Logistics to phase 2

Food, accommodation, transport and live location are a second product. Launch with the thin slice: apply → approve → event → register → pass → duty → check-in. Pilot it in one state, then add logistics module by module.

Design system

Saffron for action, ink for everything else

Saffron is used only where the person must act or look: the primary button, the pass tab, today's card. The rest is quiet ink and grey, so the screen stays calm even with a lot of data. Status always shows as a coloured pill with words, never colour alone.

Rules

  • One primary (saffron) button per screen.
  • Touch targets at least 44 px; body text never below 14 px on phones.
  • Phone numbers are never shown in lists; a call button appears only where the role allows it.
  • Light and dark themes from the same tokens.

Mobile app · Flutter · Android and iOS

Seven screens that carry the whole journey

Bottom navigation has five places: Home, Events, Pass, Duties, Me. Pass sits in the middle and raised, because at the gate it is the only thing that matters. Scroll sideways to see all screens.

App navigation

PassEvent QR (or member QR when no event is active)
DutiesAssigned duties, acknowledge, report done or problem

Role tools inside the same app

ScanCheck-in volunteers: scan pass, see name and photo, mark arrived. Works offline, syncs later.
TeamTeam leads: see their team, mark duties in progress, done or blocked.
GuestGuests: invitation, pass, venue and contact only. No member features.
ApproveDistrict admins on the move: a simple approvals list. Full review stays in the web admin.

Web admin · React, built as static files

An admin panel that only shows your scope

A fixed left sidebar, a scope switcher at the top, and content below. The panel is designed for a district office laptop at 1366 px. Switch between three key screens.

Running on Hostinger shared hosting

Designed to fit the hosting you already have

Shared hosting runs PHP well and nothing long-running. So the API is Laravel, the admin is a static React build, background work runs from cron in small batches, and live screens refresh by polling. Nothing in the design depends on a server that stays awake.

People use
Flutter appAndroid and iOS. Caches pass, duties and event details for offline use.
Admin paneladmin.abvpconnect.inStatic React files, no Node server needed.
Public websiteabvpconnect.inDownload links, event pages, guest invitation links.
Hostinger shared plan
Laravel APIapi.abvpconnect.in → /public onlyREST /api/v1, roles and scopes checked on every request, audit log.
MySQL (Hostinger, same server)My suggestion for the pilot: no outbound-connection risk and nothing extra to pay. Move to managed PostgreSQL or MySQL when you scale.
Cron, every minuteschedule:run · queue:work --stop-when-emptySends push and SMS in batches, builds report exports, expires passes.
Outside services
DigitalOcean SpacesPhotos and documents. Private files through short-lived signed links.
SMS OTP providerDLT-registered Indian sender, for example MSG91.
Firebase Cloud MessagingPush notifications, free tier.
MapsOpen in Google Maps by link. No paid map SDK in phase 1.
Shared hosting limitHow the design responds
No WebSockets or always-on processesCommand centre polls every 15–20 s and shows "Updated 12 s ago" so nobody expects instant updates.
CPU and memory caps, traffic spikesPass check-ins go through one small endpoint; scanners batch offline check-ins. Event lists are cached as JSON for 60 s.
Limited disk and slow uploadsPhotos are resized on the phone to under 300 KB before upload, and stored on Spaces, not Hostinger.
Cron runs at most every minuteNotifications say "within a few minutes"; OTP SMS is sent directly in the request, not queued.
When to move offBefore the first multi-state event with more than about 5,000 people on one day, move the API to a Hostinger VPS. The code does not change.
